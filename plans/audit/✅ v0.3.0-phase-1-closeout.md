## Executive Summary

Phase 1 delivers the **server-side foundation** for Drive import, per spec
§1.1–§1.4 (Security Hardening + Drive Download Client). No UI changes —
Phases 0 (transport) and 1 (server) are deliberately independent so the
production import flow can be built on a settled, tested boundary.

1. **Server-side download client** — `download_drive_file()` in
   `utils/drive_client.py` with 3-layer size validation, server metadata
   authority, MIME allowlist, and typed error categories
2. **Component wrapper hardening** — `components/drive_picker_component.py`
   validates the raw component result structurally into `PickerSelection` or
   `None`; Picker metadata is stripped at the boundary
3. **Token-safety enforcement** — new source-scan tests guarantee no
   credential variables reach display/logging/exception paths and no
   `exc_info=True` in Drive error handlers
4. **AST scope guard extension** — `TestDriveScopeRestricted` rejects
   `drive`, `drive.readonly`, `drive.metadata.readonly` at the token level
   while allowing `drive.file`
5. **Frontend CI gate** — GitHub Actions job runs `npm ci` → typecheck →
   production build → bundle-artifact assertion

## Security notes

- OAuth token and Picker key are passed only as declared-component runtime
  arguments (never HTML-embedded, logged, displayed, or persisted) — D3
- The component return contract is `{kind, requestId, fileId}` only; Picker
  name/MIME/URL metadata is discarded — server `files.get()` is authoritative
- Drive errors are classified into user-facing messages; logs carry only an
  allowlisted category/status — no raw API text, request URLs, file IDs, or
  exception representations
- This phase is **server-side only** — no real Picker file ID reaches the
  application until Phase 3 (Phase 2 uses an injected fake downloader)
