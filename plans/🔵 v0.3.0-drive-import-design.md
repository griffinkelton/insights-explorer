## Architecture Decision: Picker vs. Direct Listing API

**Decision: Use the Google Picker API.**

| Factor | Picker API | Direct listing (drive.files.list) |
|---|---|---|
| UX | Familiar Google file browser with search, folder navigation, and preview | Custom-built file browser — significant UI effort |
| Consent scope | `drive.file` (existing v0.1.0 scope) — no expansion | `drive.readonly` — scope expansion, broader data exposure |
| File visibility | User explicitly selects each file | App can list all files — privacy concern |
| Maintenance | Google maintains the picker UI | App maintains a custom file browser indefinitely |
| Security | Token stays in the picker iframe — app never enumerates Drive | App code has access to file listing — broader attack surface |

The Picker API avoids scope expansion, provides a polished UX, and keeps the app's Drive footprint minimal. The app never lists files the user hasn't explicitly selected.

## Consent UX

### What the user sees

1. **Sidebar button:** "📂 Import from Drive" (only visible when OAuth credentials are valid)
2. **Click → Google Picker:** A modal file browser opens showing Google Sheets, CSVs, and XLSX files
3. **Select file → confirm:** Picker returns the selected file ID
4. **App downloads + ingests:** The file is downloaded server-side and processed through the existing data loader pipeline

### Privacy copy (sidebar, README, Learn page)

> **Drive import:** Uses your existing `drive.file` permission. The app can only access files you explicitly select through the Google file picker — it never lists or reads your Drive contents. Imported files are processed session-only and never stored to disk.

### Authorization flow

- No new OAuth scopes required — `drive.file` is already granted in v0.1.0
- If OAuth is not configured, the button shows "Sign in with Google to import from Drive"
- Token refresh follows the existing v0.1.0 OAuth flow (session-only, never persisted)

## Security Checklist

### Scopes

- [ ] **Existing scope reused:** `drive.file` — no scope expansion
- [ ] **Scope justification:** `drive.file` grants per-file access only to files the user opens/creates through the app. The picker interaction creates a file-level grant for the selected file.
- [ ] **AST guard:** `test_static_analysis.py` extended to reject `drive.readonly`, `drive.metadata.readonly`, and `drive` (full access) scope literals

### File Constraints

| Constraint | Limit | Rationale |
|---|---|---|
| Max file size | 100 MB | Matches existing upload limit |
| Max rows | 50,000 | Matches existing upload limit |
| MIME types | `text/csv`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `application/vnd.google-apps.spreadsheet` | GA4 export formats only — no arbitrary file types |
| File origin | User-selected via Picker | App never enumerates Drive |

### Network & Processing

- [ ] File download occurs server-side only — no Drive content in browser JavaScript
- [ ] Downloaded file bytes passed through existing `data_loader` validation pipeline
- [ ] Files are never written to disk — processed in memory only
- [ ] `DataContext` created with content-derived `source_id` (SHA-256 of file bytes) — same dedup as upload
- [ ] Provenance records `"drive-import:{filename}"` — distinguishes from uploads

### Session Safety

- [ ] Imported data cleared on "Clear Data" — same lifecycle as uploads
- [ ] No Drive file IDs persisted across sessions
- [ ] OAuth tokens remain session-only (existing v0.1.0 behavior)

## Implementation Scope (v0.3.0)

### Phase A: Picker Integration

1. Load the Google Picker API script (gapi) in the Streamlit page
2. Render a "📂 Import from Drive" button in the sidebar
3. On click, open the Picker configured for spreadsheets + CSVs
4. Receive the selected file ID via postMessage
5. Download the file using the existing Drive client (`utils/drive_client.py`)
6. Pass bytes through `data_loader` → create `DataContext`

### Phase B: Security Hardening

1. Extend AST guard to reject broader Drive scopes
2. Add MIME validation before parsing
3. Add file size check before download
4. Add row count check after parsing
5. Log audit metadata: file name (not path), MIME type, size, row count, timestamp

### Phase C: UX Polish

1. Loading state during download + parsing
2. Error states: file too large, unsupported type, parse failure, picker cancelled
3. Success confirmation with file name + row count
4. Update README, Learn page privacy section, and inline help

## v0.1.0 Safety Baseline Preservation

The v0.1.0 hardening release established least-privilege OAuth, session-only token handling, AST-based scope guards, and a zero-persistence data model. The Drive Import feature preserves every one of these:

| v0.1.0 Principle | How v0.3.0 Preserves It |
|---|---|
| Least-privilege scopes | Reuses `drive.file` — no expansion needed |
| Session-only tokens | OAuth flow unchanged — tokens never persisted |
| AST scope guards | Extended to reject broader Drive scopes |
| Zero file persistence | Downloaded bytes processed in memory, never written to disk |
| Content-derived identity | `source_id` uses SHA-256 of bytes, same as upload flow |
| Clear Data semantics | `clear_data()` removes Drive-imported `DataContext` identically |

## Deferred to Future Versions

- **Scheduled/bulk Drive imports:** Manual single-file picker only for v0.3.0
- **Direct folder access:** Picker filters to individual files — no folder browsing
- **Drive file change detection:** No polling or webhook-based refresh
- **Google Sheets formula preservation:** Raw values only; formulas are materialized
- **Shared Drive support:** Personal Drive only for v0.3.0
